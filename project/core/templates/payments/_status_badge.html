{% comment %} THE payment-status badge. It was hand-written as a five-branch chain in four templates and the copies had drifted: all_info.html hard-coded its own labels, coloured `pending` red and had no `refunded` branch at all (a refunded payment rendered no badge there). The label always comes from `get_payment_status_display`, so a renamed status cannot leave a stale word behind. Include with: {% include "payments/_status_badge.html" with payment=payment classes="" %} {% include "payments/_status_badge.html" with payment=payment classes="px-3 py-1 text-sm font-medium" show_days=True %} `classes` sets the size — pass `classes=""` for the compact list default. ALWAYS pass it, even when empty: reading a variable that is not in the context logs a full `VariableDoesNotExist` traceback to `django.template` at DEBUG on EVERY render, so a 50-row payments list wrote 50 tracebacks per page load in development. `{% firstof %}` does NOT avoid that — the log happens inside `Variable._resolve_lookup`, before `ignore_failures` is consulted, so it behaves exactly like the `|default:` filter here. The only thing that silences it is the variable existing. `show_days` appends "(N días)" to an overdue badge.
