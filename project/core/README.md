# core — Dashboard, Auth, Schedule, Shared Utilities

The `core` app is the "everything else" app — it owns the dashboard, authentication, scheduling, and lightweight cross-cutting models that don't belong to a specific domain.

## Models

| Model | Table | Purpose |
| ----- | ----- | ------- |
| **ScheduleSlot** | `schedule_slots` | Weekly schedule grid (row, day, col) with group FK |
| **FunFridayAttendance** | `fun_friday_attendance` | Tracks student attendance on Fun Fridays. Indexed on `date` since v1.26.1 — the `(student, date)` unique constraint leads on `student`, so the date-only lookup that runs twice per students-list and schedule page load was a sequential scan on a table that grows by one row per student per Friday |
| **FunFridayScheduledSend** | `fun_friday_scheduled_sends` | Persisted Fun Friday announcements awaiting their scheduled send time (drained by `core.tasks.send_due_fun_friday_emails_task`) |
| **TodoItem** | `todo_items` | Dashboard task list with due dates |
| **HistoryLog** | `history_logs` | Audit trail of user actions (auto-capped at 1,000 with guarded single-query cleanup). v1.27.1 adds the `enrollment_modality_changed` action (migration `0015`): a cadence change now **supersedes** the enrollment rather than mutating it, so it is its own event — reusing `student_enrolled` made the feed read as a fresh enrollment, which is exactly the kind of history nobody can reconstruct a billing dispute from. Declared in `ACTION_CHOICES` so `get_action_display()` does not fall through to the raw slug |
| **BacklogTask** | `backlog_tasks` | QA-only bug/feature reports filed from the `/app/testing/` dashboard. Marking one done emails the admin teachers; `core.tasks.cleanup_done_backlog_tasks` deletes rows done > 30 days ago. `verified` (v1.20.0) is the **tester's** tick — deliberately independent of `status="done"`, which is the developer's and sends the notification. `feature` (v1.21.0) is the optional `SET_NULL` FK back to the **Feature** the task was broken out of |
| **Feature** | `features` | v1.21.0 QA *desarrollo* — a Jira-style epic grouping the backlog tasks that deliver it. Deliberately lighter than `BacklogTask`: **no priority** (an epic is scheduled by its `deadline`, not ranked against its siblings) and **no screenshot** (it describes work to build, not a defect seen on screen). `deadline` is nullable and `None` by default — a development is recorded long before anyone commits to a date. `is_overdue` only fires when the date has passed **and** the epic is not done |
| **QAConfiguration** | `qa_configuration` | QA-only singleton holding the error-email toggle and `ready_for_prod` (v1.26.4). `drive_uploads_enabled` was **removed in v1.29.10** (migration `core/0018`): the archive now authenticates as a delegated Google account, and that consent cannot be completed on the QA VM at all, so the toggle was a control nobody could reach — QA's sign-off that the deployed version may ship to production. Set by the "¿Listo para desplegar?" button, reset by every nightly testing deploy, read by `deploy-production.yml`'s preflight through `/health/?deep=1` |
| **AuditLog** | `audit_logs` | v1.10 immutable per-model change trail (`audit_models.py`), written by the `post_save`/`post_delete` receivers in `audit_signals.py` with a contextvar-supplied actor. Its `pre_save` snapshot reuses the row `students.models._capture_active_transition` already fetched (`instance._presave_db_obj`) — both receivers needed the same row and each was issuing its own `objects.get()`. **v1.27.1: `object_label` is PII-minimised.** It defaulted to `str(instance)`, which for `Parent` renders `"Nombre Apellido (DNI)"` — so the DNI of every parent in the academy was written into a searchable log retained for two years, the one field the per-model field allow-list goes out of its way to **exclude** from `changes`. Minimising the payload and then leaking the same datum through the label defeats the whole exercise. `audit_signals._object_label()` prefers an `audit_label` attribute; a model opts out by exposing one (`Parent.audit_label` = name + pk), and everything else keeps `str(instance)`, so no other label changed |

## Middleware & Decorators

- **`RequestLogMiddleware`** (`middleware.py`, v1.29.7) — **FIRST in `MIDDLEWARE`**, deliberately: it binds the correlation id that every other record in the request is stamped with, so anything logged below it — including `SecurityMiddleware`'s SSL redirect — is joinable. Two jobs. **The id**: one failure writes several records from several modules, and with nothing in common they can only be joined by comparing clocks, which is what a production welcome-email failure cost (three alert mails, one incident, no way to prove it). The id is echoed as the `X-Request-ID` response header so a user reporting a problem can quote the exact request, and it appears in both the `mail_admins` alert and the QA error mail. An inbound `X-Cloud-Trace-Context` is preferred over an inbound `X-Request-ID` — Cloud Run sets it, and reusing it as the correlation id means one string finds the request in Cloud Logging *and* every record the app wrote for it — but both go through `sanitize_request_id` / `sanitize_trace_id`, which **replace** anything unrecognised rather than cleaning it: the header is client-controlled, a newline in it forges log records, and a partially-scrubbed id is no longer the id the client is quoting. The id is released in a `finally`, because Gunicorn reuses threads and one left bound leaks onto whatever that worker serves next. **The line**: one per request, levelled so the noise is proportionate — 5xx → ERROR, slow → WARNING past `settings.SLOW_REQUEST_LOG_MS` (3 s; a nine-second success is invisible in every other log we keep), 4xx → INFO, everything else → DEBUG, i.e. nothing in production. A 5xx **Django already logged** drops to INFO instead: `django.request` logs the traceback at ERROR and that is what mails the admins, so a second ERROR would mean two alerts per incident out of two throttle buckets — the flag is set by a `got_request_exception` receiver connected in `core/apps.py`. A 5xx a view *returned* rather than raised stays at ERROR, because nothing else logs it at all. It logs the resolved **URL name**, never `request.path`, which is attacker-controlled free text (CodeQL `py/log-injection`) and groups badly.
- **`SimpleAuthMiddleware`** (`middleware.py`) — access control in **three** parts as of v1.27.1.
  - **Layer 0 (the parent portal)** — `/parent/…` is a separate authentication domain with its own session key (`parent_id`), checked first and never subject to the staff login redirect or the teacher whitelist. It used to sit in `PUBLIC_PREFIXES` as a blanket `/app/parent/`, which exempted every current **and future** portal URL from authentication: a new portal view was public until somebody remembered to call `_require_parent` inside it. The prefix is now **default-deny**, with the genuinely public URLs enumerated in `PORTAL_PUBLIC_URL_NAMES` (`parent_portal_login`, `parent_portal_forgot_password`) and `PORTAL_JSON_URL_NAMES` (`stripe_create_checkout_link`) answering **401 JSON** instead of a 302 to an HTML login page, which is what `fetch()` needs. The views' own `_require_parent` remains the real check — it also verifies the credential stamp and the must-change-password pin; this is the net under it. **Since v1.29.4 the layer opens with the portal KILL SWITCH**: while `settings.PARENT_PORTAL_ENABLED` is off (the default) every `/app/parent/` URL raises `Http404`, the public login and recovery pages included, so a family holding an old link finds nothing rather than a form that cannot help them. It is one of exactly three readers of the flag — the other two are `parent_portal.send_portal_temporary_password` / `send_portal_invitation_once` and `students.admin.ParentAdmin.resend_portal_invitation` — and it is a switch rather than a URL deletion because the mailer's `reverse("parent_portal_login")` would otherwise raise `NoReverseMatch`, turning a flag into a refactor.
  - **Layer 1 (authentication)** — all URLs are protected except the public prefixes (`/app/login/`, `/health/`, `/static/`, `/media/`, `/auth/google/*`, `/password-reset/*`, the Stripe webhook, the PWA manifest/service worker, the mid-login 2FA gate); unauthenticated requests are redirected to login. **The session flag is no longer sufficient (v1.27.1)**: `_session_identity_revoked()` rejects a session whose backing identity can no longer be resolved or is no longer active, flushes it and redirects with a Spanish message. Nothing ever revoked `is_authenticated`, and `SESSION_COOKIE_AGE` is 6 h with `SESSION_SAVE_EVERY_REQUEST=True`, so an open tab renewed it indefinitely — but the real problem was worse than an offboarded teacher keeping their own access: all three offboarding actions (deactivating the `auth.User`, deactivating the Teacher, **deleting** the Teacher) make `ModelBackend.get_user` refuse the id, `request.user` becomes `AnonymousUser`, `_is_non_admin_teacher` answered "not a non-admin", and the session was handed the **unrestricted** set — `/payments/`, `/app/database/`, the `/app/management/` write endpoints. **Revocation escalated the session.** `_session_has_django_identity()` distinguishes "no Django identity was ever claimed" (the test suite's `authenticated_client` shape — left alone) from "one was claimed and can no longer be resolved" (rejected), and the `is_superuser` / `is_staff` hatches are preserved because the dev env-var login and every OAuth session are free-standing superusers with no Teacher row.
  - **Layer 2 (authorization)** — when the session user is a non-admin Teacher (`teacher.admin=False`), requests are restricted to the `NON_ADMIN_ALLOWED_URL_NAMES` whitelist; admin-only routes redirect to the dashboard with a flash message (403 JSON for `/api/*`). **`_is_non_admin_teacher` now fails CLOSED** (v1.27.1): an unresolvable-but-claimed Django identity is *restricted*, never trusted — the predicate is also read by `today_notifications` with no gate in front of it, so the safe answer has to live here too. And **`Teacher.active` is checked BEFORE the `is_superuser`/`is_staff` hatch**, because the Teacher `post_save` signal mirrors `Teacher.admin` onto *both* flags: a deactivated **admin** teacher still carried them, so testing the flags first handed the full unrestricted set to somebody who had just been let go. An ordinary `auth.User` with no Teacher row is now rejected outright rather than merely restricted — there is no legitimate account of that shape.

  Keep the whitelist in sync with `core/urls.py` and the per-app urls; since v1.27.1 it is a *second* control rather than the only one (see `admin_required`). **v1.26.8 tightened it**: students are read-only for a non-admin teacher (`student_create`, `student_update`, `parent_create` and the new `enroll_student` are out), `assign_from_waiting_list` is out too (it redirects into the `parent_create → student_create` flow, i.e. enrolling by another name), and `history_list` is out because the header bell and the actions-history feed are now hidden from non-admins in `base.html`. `change_password` was added — changing your own password is self-service, not an admin write. **v1.27.1 removes expenses entirely** (`expenses_list`, `create_expense`): the previous read-plus-create compromise never had a rationale that survived being written down — `expenses_list` **is** the academy's profit-and-loss for the month (every rent, salary and software line, plus the totals), exactly the class of figure the trimmed non-admin dashboard exists to withhold, and `create_expense` is a financial write against it. The sidebar has always hidden the Gastos link from this role, so the page was reachable only by typing the URL: nobody was using it, and the two entries were pure latent grant. Reports went the same way in v1.26.8.
- **`QAErrorEmailMiddleware`** (`middleware.py`) — in the QA environment, catches unhandled exceptions and emails them to `SUPPORT_EMAIL` with the full traceback. Toggleable via the `/app/testing/` dashboard. **v1.23.0:** it is now gated on `IS_TESTING_ENV` and `_redact_body` strips credential fields from the 500-char body preview. The flag lives in the database and the middleware previously honoured it *anywhere* it was set — including production, where the dashboard that toggles it is unreachable but the row is still writable from a shell — so an exception on the login POST emailed `username=…&password=…` in cleartext. Redaction covers **both** urlencoded and multipart bodies; urlencoded alone would cover the login form and silently miss every multipart POST. **v1.28.1 added `_redact_json`**: the redactor bailed out on `"=" not in raw`, so a JSON body — which is what *every* `/api/` POST sends, including both password-change endpoints — fell straight through and reached the inbox verbatim. It blanks sensitive values in a possibly truncated preview, since the body is cut to 500 chars before it is ever parsed. **v1.27.1 audited `REDACT_KEYS` against every write path in the app** rather than growing it anecdotally, because the miss is silent — the key is simply absent, the value is mailed in cleartext, and nothing fails. The inventory is written out in the source, endpoint by endpoint; the one that was actually missing was **`confirm_password`**, which `/api/password-change/` posts carrying the same plaintext as `new_password`, so a 500 in the change-password flow on the QA VM mailed the new staff password to `SUPPORT_EMAIL` — the second time that list had been short by exactly one confirm field. The rest are defensive aliases for the same concepts (`otp`, `backup_code`, `totp`, `verification_code`, `access_token`, `client_secret`, `probe_token`, …) so a new form naming its field differently does not have to remember to come back here, plus `dni` and `iban`, which are not credentials but are regulated data about minors' families.
- **`RedactingExceptionReporterFilter`** (`middleware.py`, v1.27.1) — wired up as `DEFAULT_EXCEPTION_REPORTER_FILTER`, so it governs the debug 500 page **and** the body of every `AdminEmailHandler` mail (production alerting, via `settings.ADMINS`). Django's `hidden_settings` regex covers settings and local variables, **not** the request body: `POST` is only cleansed when the view opted in with `@sensitive_post_parameters`, which Django's own auth views do and **none** of this app's hand-rolled ones do (`login_view`, `change_password`, `two_factor_verify`, `parent_portal_login`, `parent_portal_change_password`). Without the subclass an error report from any of them carried the submitted password verbatim. It reads the **same** `QAErrorEmailMiddleware.REDACT_KEYS`, so there is one place to add a field name, and it `copy()`s before writing — `super()` hands back `request.POST` *itself*, an immutable `QueryDict`, whenever the view did not use `@sensitive_post_parameters`.
- **`NoHtmlCacheMiddleware`** (`middleware.py`) — sets `Cache-Control: no-cache, no-store, must-revalidate` on every `text/html` response. Content-hashed static assets are served `immutable` for 10 years, so a browser-cached HTML page would pin *old* asset hashes and leave the theme stale after a deploy. Sits right after WhiteNoise in `MIDDLEWARE`.
- **`SecurityHeadersMiddleware`** (`middleware.py`, v1.23.0) — adds Content-Security-Policy and Permissions-Policy to every response. CSP ships **report-only** until `CSP_ENFORCE` is set, so a missed inline script surfaces as a console report rather than a blank page.
- **`AuditActorMiddleware`** (`audit_signals.py`) — stashes the current user in a contextvar so the `AuditLog` signal receivers can attribute a change without threading the request through the ORM.
- **`qa_access_required`** (`decorators.py`) — reusable gate for `/app/testing/` views and endpoints. A deny-by-omission allowlist is the right shape, but the check lives in a file nobody edits when they add a URL: forgetting an entry *blocks* something (loud and obvious), while forgetting to keep an entry **out** grants a privilege silently, and nothing at the view itself said who may call it. Two independent controls now have to agree. The response shape **mirrors the middleware exactly** (403 JSON under `/api/`, otherwise a flash message and a redirect to the dashboard; `redirect("login")` when there is no session at all) so a blocked caller cannot tell which layer stopped them and the frontend needs no second error branch. It reuses `core.middleware._is_non_admin_teacher` — imported lazily to keep the module cycle-free — so the two layers cannot disagree about what "admin" means.

## Input & Output Guards (`utils.py`, `rate_limit.py`)

- **`csv_safe(value)` / `csv_safe_row(values)`** (`utils.py`) — neutralise CSV formula
  injection (CWE-1236). A cell beginning `=`, `+`, `-` or `@` is evaluated on open, and
  student and parent names are free text a **non-admin** teacher can set, so the payload
  executes on a more privileged user's workstation. Only `str` values are touched, so a
  negative `Decimal` keeps its leading `-`.
- **`xlsx_safe_append(ws, values)`** (`utils.py`, v1.26.0) — the same threat in `.xlsx`,
  where the apostrophe trick does **not** work. openpyxl inspects every string and marks
  one starting with `=` as `data_type="f"`, so the workbook contains a *real* formula
  rather than text a spreadsheet might evaluate; a leading `'` would just be stored
  verbatim and rename the student. The guard writes the row and forces the cell back to a
  string. `billing/exports.py` is the only openpyxl consumer and routes every row through it.
- **`safe_int(raw, *, default, low=None, high=None)`** (`utils.py`, v1.26.0) — parse an int
  from request input, falling back to `default`. The **range** matters as much as the parse:
  Django builds a real `date(year, 1, 1)` for a `__year` lookup, so `?year=-5` raises
  `ValueError` and `?year=99999999999` raises `OverflowError`, both past an
  `except (TypeError, ValueError)` that only wraps the `int()` call. This had been written
  three times in three modules while two further views were still missing it.
- **`rate_limit(scope, ...)`** (`rate_limit.py`) — throttles login, 2FA, password reset and
  the parent-portal credential emails per client IP. **v1.26.0:** counts with `limit` one-shot
  slots claimed via `cache.add()` instead of `add()` + `incr()`. `DatabaseCache` — the
  backend production runs — does not override `incr`, so it inherited `BaseCache.incr`, a
  plain get-then-set, and concurrent attempts were lost; `add()` is a primary-key INSERT
  exactly one racing caller can win. It also swallows `DatabaseError` and returns False,
  which is indistinguishable from a taken slot, so `_claim_slot` probes with `cache.get()`
  (which does not swallow) to tell a full window from an unreachable cache — that probe is
  what preserves the deliberate **fail-open** behaviour.

## Shared Querysets (`transactions.py`)

Pre-built, `select_related`/`prefetch_related`-optimised queryset builders, returned fresh per call (never evaluated at module import).

- **`students_on_the_roll(*, children_only=False)`** (v1.29.1) — students actually studying THIS course, as every page means it: `active=True`, not a waiting-list placeholder, and holding an enrollment in one of `relevant_academic_years()` (BOTH cohorts during the May–August overlap, or half the academy disappears from the list for four months of every year), `.distinct()` because the enrollment join multiplies a student by their enrollments. One definition because there were three — the students list, the Fun Friday page and the re-enrolment candidate pool each spelled it out inline, so "who is on the roll" could be answered differently on three pages of the same app, and fixing it in one (a waiting-list entry leaking into Fun Friday) did not fix it in the others. `children_only` drops adult students, who have no guardian and do not take part in the children's activities.
- **`visible_students_for(request, queryset=None)`** (v1.29.4) — narrows a `Student` queryset to what the REQUESTING session may see: a non-admin teacher gets only the students in the groups they teach (`Group.teacher`), an admin gets the queryset back untouched. THE one place that rule is written, because it has to hold on every surface that lists or opens a student — the roll (`StudentListView`), the ficha (`StudentDetailView.get_queryset`, where an unscoped view let a teacher read any family's phone number and address by typing an id), the autocomplete (`search_students`) and `management.language_cheque_students`. Spelling it out per view is how the four would drift, and the drift is silent: it is invisible to admin testing, because admins take the early return. Two deliberate edges — **waiting-list placeholders stay visible** (a waiting entry is nobody's student yet, usually has no group, and managing that queue is in this role's whitelist; scoping them out would 404 a teacher on the ficha they had just created), and a restricted session with **no Teacher row sees nothing**, which is how every other control here fails.

## Logging Helpers

- **`safe_log(value, max_len=200)`** (`log_safe.py`, v1.14.4) — single-line, length-capped rendering of anything user-controlled that is about to be formatted into a log record. Strips `CR`/`LF`/`VT`/`FF`/`ESC` so an attacker-supplied field can't forge extra log lines (CodeQL `py/log-injection`) or smuggle terminal escapes into a tailed log, and truncates at 200 chars so one field can't flood the log. Stdlib-only leaf module — no Django, no models — so any app can import it without a cycle. **Use it for every log call whose value comes from a request** (headers, query string, form body, URL captures). `comms` carries its own copy at `comms/log_safe.py` instead of importing this, because `comms` must not depend on `core`; both are pinned against each other by `tests/unit/test_log_safe.py`. **Note (v1.14.5):** this does not silence CodeQL's `py/log-injection` — the query treats `str.replace` as taint-preserving. For ids, coerce with `int()` and `%d`; for free-form values, prefer not logging them or validating them into a known shape (see `_client_ip`).
- **`logging_utils.py`** (v1.29.7) — the structured-logging layer, and **stdlib-only for the same reason `log_safe` is**: `dictConfig` instantiates these while Django is still starting, long before the app registry is ready, so importing models or settings here would be a boot-time cycle.
  - **`CloudLoggingFormatter`** — one JSON object per line carrying an explicit `severity`, `logging.googleapis.com/sourceLocation`, and (when `GOOGLE_CLOUD_PROJECT` is set) `logging.googleapis.com/trace`, which is what makes Cloud Logging nest our entries *inside* the Cloud Run request log rather than beside it. The explicit severity is the point: `StreamHandler` defaults to **stderr**, Cloud Run labels everything on stderr as ERROR, and so every `logger.info` line arrived in production indistinguishable from a failure — the console's severity filter, the first control anyone reaches for mid-incident, selected the whole log. The handler now writes to **stdout**. The trace field is only emitted fully qualified; a bare id is silently dropped by Cloud Logging, and one is never fabricated, which would file our records under a request that never happened. Exception text is appended to `message` as well as carried separately, because the Logs Explorer preview row shows only `message` and a traceback living solely in a collapsed field is one nobody reads while the site is down.
  - **`HumanFormatter`** — the readable line for dev and the QA VM, which are read by a person through `docker compose logs`. Carries the logger **name and line number** (`{module}` alone cannot tell two modules apart that log the same sentence) and prefixes the correlation id only when there is one. `LOG_FORMAT=json|text` picks between the two; the default is json in production and text everywhere else.
  - **`RequestContextFilter`** — stamps `request_id` on **every** record, ours and Django's alike. Attached **per handler, not per logger**: a logger's filters do not run for records that merely propagate up to its handlers, so putting it on `root` would have missed every record from `core` and `django`.
  - **The context variables and sanitizers** — `set_request_id` / `reset_request_id` and the trace pair, plus `sanitize_request_id` / `sanitize_trace_id`. Set per request by `RequestLogMiddleware` and per task by `project/celery.py`, where a task **inherits** the request's id when there is one (production runs eager, so a task usually *is* part of a request) and falls back to the task id only for work with no request behind it — Beat, a Cloud Run Job, a management command. Overwriting rather than inheriting would split one incident in two again. `project/celery.py` also logs one ERROR per terminal `task_failure` naming the task and its cause — never its arguments, which carry recipient addresses and ids.

## Management Commands

- **`prune_audit_log`** (v1.15) — deletes `AuditLog` rows older than `--days` (default `AUDIT_LOG_RETENTION_DAYS` = 730). Wraps `core.tasks.prune_audit_log` so Cloud Scheduler can run it as a Cloud Run Job; production has no Celery Beat. The audit trail has no row cap and writes ~16 rows per student per academic year. **v1.27.1 adds a retention floor and a `--dry-run`.** `days` must be at least `core.tasks.MIN_AUDIT_RETENTION_DAYS` (400 — a full academic year plus a margin, so a run can never destroy the trail for the course being taught, which is the one an audit question is most likely to be about). This is the *only* code path that deletes from a table the admin deliberately makes immutable, so the whole point is that ageing rows out is a policy and not a person: `--days 0` would delete every row including today's, a negative value reaches into the future, neither is a retention policy, both are a typo, and either erases the entries incriminating whoever ran it. The task raises `ValueError` and the command re-raises it as a `CommandError`, so a Cloud Run Job reports a clean failure instead of a Celery traceback. `--dry-run` returns `{"would_delete": N, "deleted": 0}` and writes nothing.
- **`purge_sessions`** (v1.23.0) — wraps `core.tasks.purge_expired_sessions` (Beat daily 03:30) so Cloud Scheduler can run it as a Cloud Run Job. Nothing purged `django_session` or `parent_session_tokens` before: session payloads are base64, signed but **not encrypted**, so anything a view puts in a session is readable by anyone who can read the table, and rows outlived their cookies forever. Add it to the production Cloud Scheduler set like the other wrappers.
- **`backup_retention`** (v1.26.0) — tiered Cloud SQL backup retention, the scheduled port of `scripts/backup_retention.sh`: creates the `tier:biweekly` (1st + 16th) and `tier:monthly` (month end) on-demand points and prunes each class to its keep-count. Dry run by default; the `fiveaday-backup-retention` Cloud Run Job passes `--apply` (Cloud Scheduler, daily 05:30). Talks to the SQL Admin REST API with google-auth + httpx; `Command.client_class` is the test seam. Warns on automated-retention drift but never patches it — that needs `cloudsql.instances.update`, which the job's role deliberately lacks.
- **`seed_testdata`** — populates the QA database with 3 teachers, 5 groups, 6 parents, 12 child students, 3 adult students, 1 inactive student, active enrollments, payments in various states, schedule slots, todo items, and history log entries. - **`seed_teachers`** — idempotently creates Teacher rows + linked `auth.User` accounts from `TEACHER_SEED_<N>_*` env vars (N starts at 1, iteration stops at the first missing `FIRST_NAME`). Each block sets `FIRST_NAME`, `LAST_NAME`, `EMAIL`, and optionally `USERNAME`, `PHONE`, `ADMIN` (defaults to false), and `PASSWORD`. `USERNAME` is an optional SHORT login handle (`claudia`) applied to the linked `auth.User` after `ensure_user()`; without it the handle is the email. A handle already taken by another account is warned about and ignored rather than aborting the boot. ## Shared Admin Action (`admin_purge.py`)

`PurgeWithHistoryMixin` (v1.29.7) adds a **second**, explicitly named delete action to a
ModelAdmin: `purge_with_history` clears the rows that `PROTECT` the selection, in FK order,
then the selection itself — behind `admin/purge_confirmation.html` and reporting the exact
per-model totals afterwards.

It exists because two deliberate protections shared one misleading message. `PaymentAdmin`
refuses to delete a collected, refunded or receipt-numbered row, and `Student` / `Parent` /
`Enrollment` are `PROTECT`ed by the rows that bill them; Django renders both as *«su cuenta no
tiene permisos»*, which reads as a broken account rather than a rule and left a record created
by mistake reachable only from a database shell.

| Property | Why |
| -------- | --- |
| Imports **only Django** | `billing.admin` and `students.admin` both use it, and naming `Payment` here would invert the documented `students <- billing` flow for one of them. Each ModelAdmin declares `purge_accessors` — reverse accessor *names* — which `_meta` resolves to a queryset with no import |
| The ordinary Delete button keeps its guard | The protection was never meant to stop a deliberate, named decision, only an accidental click |
| Superuser-only, hidden outright otherwise | Through `@admin.action(permissions=["purge"])` + `has_purge_permission`, Django's own hook — not a `get_actions` override, which on 6.1 means two APIs that go in 7.0. `Teacher.admin` mirrors onto `is_superuser`, so in practice any admin teacher; a non-admin Teacher never reaches `/app/admin/` |
| Re-selects targets by pk before deleting | A ModelAdmin queryset carries `select_related` and, on `EnrollmentAdmin`, aggregate annotations — a `GROUP BY` that has no business being in a `DELETE` |

Consumers: `StudentAdmin` (`payments` → `enrollments`), `ParentAdmin` (`payments`),
`EnrollmentAdmin` (`payments`), `PaymentAdmin` (nothing points at Payment — the action is there
purely to get past the fiscal guard).
